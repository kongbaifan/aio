## 〇、术语对齐（先把名字说对）

很多入门资料会把几个词混用，先钉死定义，后文不再歧义：

| 术语 | 正确含义 | 不是什么 |
|---|---|---|
| **LLM** | 大语言模型，系统的推理/语言能力来源 | 不负责调度，不存储知识 |
| **RAG** | Retrieval-Augmented Generation，检索增强生成。先从知识库检索相关内容，再喂给 LLM 生成 | 不是数据库本身，是"检索+生成"这套机制 |
| **Tool / Function Calling** | LLM 通过结构化调用使用的外部能力（搜索、代码执行、API…） | —— |
| **MCP** | Model Context Protocol，模型上下文协议。Anthropic 提出的**开放标准**，统一 LLM 与外部工具/数据源的连接方式，相当于"AI 世界的 USB-C 接口" | **不是调度器**，不负责分配任务 |
| **Orchestrator / 编排器** | 任务拆解、Agent 调度、状态管理、冲突处理的中枢。对应 LangGraph 的 supervisor、AutoGen 的 GroupChatManager | 业界**不叫** MCP |
| **Agent** | LLM + 记忆 + 工具 + 目标，能自主决策"下一步做什么"的单元 | 不是单纯一次 LLM 调用 |
| **SubAgent** | 由主 Agent / 编排器临时派生、完成单一子任务后销毁的子智能体 | —— |

> ⚠️ **最常见的错误**：把"调度中枢"叫成 MCP。MCP 解决的是"怎么把工具接进来"，编排器解决的是"谁来干、按什么顺序干"。两者是不同层。

## 一、整体分层架构

```
┌─────────────────────────────────────────────────────────┐
│  用户 / 业务入口                                          │
└───────────────────────────┬─────────────────────────────┘
                            │ 复杂目标
┌───────────────────────────▼─────────────────────────────┐
│  编排层 Orchestrator                                      │
│  · 任务拆解（借助 LLM 理解）                              │
│  · Agent 调度与资源分配                                   │
│  · 状态管理 / 流程控制（确定性代码为主）                  │
│  · 冲突检测、重试、结果一致性校验                         │
└──────┬───────────────┬───────────────┬──────────────────┘
       │               │               │
┌──────▼─────┐  ┌──────▼─────┐  ┌──────▼─────┐
│  Agent A   │  │  Agent B   │  │ SubAgent…  │   ← 执行层（可并行）
│ LLM+记忆+  │  │            │  │（用完销毁）│
│  工具      │  │            │  │            │
└──┬───┬───┬─┘  └────────────┘  └────────────┘
   │   │   │
   │   │   └──────────► 工具层 Tools / MCP
   │   │               （搜索、代码执行、API、文件…）
   │   │
   │   └──────────────► RAG 知识层
   │                   （向量库检索 + 知识溯源）
   │
   └──────────────────► 上下文记忆层
                       （短期对话 / 长期记忆 / 共享状态）
```

四条横向支撑（记忆、RAG、工具、LLM 池）服务于所有 Agent，由编排层统一管控访问权限。

## 二、核心组件详解

### 1. LLM 推理引擎

系统的"思考能力"来源，负责理解、拆解、推理、生成、总结。

**关键工程要点：**

- **分级使用算力**：复杂推理用大模型，简单重复任务（格式转换、分类、抽取）用小模型甚至传统脚本。**不是所有任务都该上大模型**——成本和延迟会爆炸。
- **输出不确定**：同样输入可能给不同输出。关键任务需做一致性校验或多数投票。
- **温度参数**：要稳定/事实性的任务用低温（0.1–0.3）；要创意的任务用高温。
- **结构化输出**：要求以 JSON / 固定 schema 输出，便于编排器解析与校验。

> 💡 **重要直觉**：每次 LLM 调用 = 真金白银的 token + 几秒延迟。这与"CPU 核心几乎免费"完全相反。**成本和延迟是真实系统的头号约束**，多 Agent 设计必须时刻权衡。

### 2. RAG 知识层

让 LLM 基于**外部可信知识**回答，而非凭记忆编造。

**检索流程：**

```
用户/任务查询 → 向量化 → 在向量库中检索 Top-K 相关片段
            → 重排序(rerank) → 拼进 Prompt → LLM 生成带依据的回答
```

**质量控制（RAG 的真正难点）：**

- **知识溯源**：每条入库数据保留来源 + 时间戳。
- **分区与可信度分级**：高可信区（官方文档/权威报告）、中可信区（新闻/博客）、低可信区（UGC/社媒）。检索时按需路由。
- **冲突标记**：检索到互相矛盾的信息时，标记冲突并展示所有来源，不擅自取舍。
- **防知识污染**：错误的中间结果一旦写回向量库，会毒化后续所有检索。写入需经验证。
- **定期清洗**：清理过时、重复、错误知识。**库不是越大越好**——过大降低检索速度与准确率。

> ⚠️ **误区**：检索的信息不是越多越好。过多无关内容会稀释注意力、降低生成质量。每个子任务应只检索必要的分区。

### 3. 工具层 Tools / MCP

让 Agent 突破"纯文本生成"，去真正执行动作。

- **Function Calling**：LLM 输出结构化调用请求，宿主程序执行后把结果回传。
- **MCP**：把工具/数据源的接入方式标准化。一个 MCP Server 暴露能力，任何支持 MCP 的客户端都能即插即用，避免每接一个工具都写一遍胶水代码。
- **常见工具**：联网搜索、代码执行（沙箱）、文件读写、数据库查询、第三方 API、绘图等。

**安全要点：** 工具是 Agent 真正"动手"的地方，需做权限隔离（只读/可写）、沙箱执行、对破坏性操作（删除、对外发送、生产变更）加确认。

### 4. 编排器 Orchestrator

整个系统的"大脑调度中枢"。职责：

- **任务拆解**：借助 LLM 把大目标拆成可并行/串行的子任务，标注依赖关系。
- **Agent 调度**：按子任务类型、Agent 能力、当前负载匹配执行单元。
- **状态管理**：跟踪每个子任务进度，处理异常、重试、超时。
- **资源分配**：管理 LLM 实例池、RAG 查询队列、工具调用配额。
- **结果汇总与一致性校验**：合并子结果；不一致时重试或多 Agent 投票。

> 🔑 **工程关键**：编排逻辑（流程顺序、依赖、重试）应尽量用**确定性代码**（状态机 / DAG）实现，**只在"理解与拆解"这种必须靠语言能力的环节才调用 LLM**。把整个调度都交给一个会幻觉的 LLM，工程风险很高。

### 5. 上下文记忆层

| 类型 | 作用 | 存在周期 |
|---|---|---|
| **短期记忆** | 当前对话/任务的上下文窗口 | 单次任务 |
| **长期记忆** | 跨会话的用户偏好、历史成果 | 持久化（常落到向量库/DB） |
| **共享状态（全局记忆）** | 所有 Agent 可读的任务目标、公共中间结果 | 任务期间 |
| **私有记忆（局部记忆）** | 单个 Agent 的执行过程、临时数据 | Agent 生命周期 |

**隔离原则**：全局记忆与私有记忆分离，避免 Agent 间互相污染上下文。修改共享数据时提交**增量**而非整体覆盖，减少冲突。

## 三、多智能体协作的四种并行模式

| 模式 | 定义 | 典型场景 | 同步成本 |
|---|---|---|---|
| **数据并行** | 同一操作处理多份独立数据 | 同时抓取 10 家公司财报 | 最低，天然无冲突 |
| **知识并行** | 同一问题从多个知识视角分析后汇总 | 从技术/市场/政策/竞品四个角度分析趋势 | 低，仅末端汇总 |
| **任务并行（流水线）** | 不同 Agent 负责流程的不同环节，有先后依赖 | 需求→架构→编码→测试→文档 | 高，串行依赖 |
| **混合并行** | 上述组合：先拆大流程，每段内再并行 | 复杂调研报告 | 视设计而定 |

**知识并行是多 Agent 相对单次大 Prompt 的核心增量价值**：多个独立视角汇总，能显著降低单一视角偏见。

> ⚠️ 每个 SubAgent 都是一次（或多次）完整 LLM 调用。"开 10 个 SubAgent 并行" ≈ 10 倍 token + 10 份 RAG 开销，不是开 10 个线程那么轻松。**能一次调用解决的，别拆成一堆 Agent。**

---

## 四、编排模式（架构选型）

中央编排只是众多模式之一，按任务特征选型：

| 模式 | 结构 | 适合 | 弱点 |
|---|---|---|---|
| **中央编排（Supervisor）** | 一个编排器统管所有 Agent | 任务边界清晰、需强管控 | 单点瓶颈，编排器本身慢且可能出错 |
| **去中心化（网络型）** | Agent 之间直接对话协商 | 开放式讨论、协商类任务 | 难收敛、易发散 |
| **层级型** | 多层 supervisor，大 boss 管小 boss | 超大规模、多团队 | 层级越多延迟越高 |
| **黑板 / 事件驱动** | Agent 不直连，读写共享状态，条件满足即触发 | 松耦合、可扩展系统 | 调试困难、时序复杂 |

## 五、冲突防护（五层）

| 层级 | 机制 |
|---|---|
| **1. 权限隔离** | 单一职责；RAG 读写权限分离；不同优先级任务用独立 LLM 实例 |
| **2. 编排层调度** | LLM 资源池管理；RAG 查询队列；结果一致性校验（轻度不一致→重试，重度→多 Agent 投票）；知识污染检测 |
| **3. 记忆层隔离** | 全局/私有记忆分离；增量更新而非整体覆盖 |
| **4. RAG 质量控制** | 知识溯源、冲突标记、版本控制、定期清洗 |
| **5. LLM 输出约束** | 统一提示词模板；事实约束（只基于检索内容回答，禁止编造）；结构化输出；温度控制 |

## 六、完整执行流程示例

**任务：写一份 2026 年 AI 手机市场调研报告**

1. 用户提出请求；主 Agent 调用 RAG 检索历史报告模板与行业背景。
2. 主 LLM 基于需求 + 检索结果，把任务拆成 6 个子任务，提交编排器。
3. 编排器调度 3 个搜索型 SubAgent，**数据并行 + 知识并行**收集出货量、华为技术、苹果技术数据。
4. 各 SubAgent 调用 RAG（对应分区）+ 搜索工具获取最新信息。
5. 结果回传编排器，存入全局记忆，**经验证后**写入 RAG。
6. 编排器调度对比分析 Agent，读全局记忆 + 检索技术对比资料，生成路线对比（**任务并行**）。
7. 趋势预测 Agent 基于全部数据 + 行业趋势资料，生成 2027 预测。
8. 写作 Agent 按分析结果 + 报告模板撰写完整报告。
9. 排版 Agent 做格式优化。
10. 编排器汇总，最终报告返回用户。
11. 报告向量化入库（高可信区），供未来复用。
12. 所有临时 SubAgent 销毁，释放 LLM 与算力资源。

## 七、常见误区速查

| 误区 | 纠正 |
|---|---|
| 所有 Agent 都该调大模型 | 简单重复任务用小模型/脚本，省算力 |
| RAG 检索越多越好 | 无关信息稀释注意力，按需检索 |
| LLM 输出一定一致 | 同输入可能不同输出，关键任务要校验/投票 |
| RAG 向量库越大越好 | 过大降低检索速度与准确率，需定期清洗 |
| 多 Agent 一定比单 Agent 强 | 多 Agent = 多倍成本+延迟+协调复杂度，只在"并行/多视角/超长任务"有真实收益时才用 |
| MCP 是调度器 | MCP 是工具接入协议；调度由编排器负责 |

---

## 一句话总结

一个好的多智能体系统 = **LLM 负责思考、RAG 负责事实、工具负责动手、记忆负责连续、编排器负责协调**；而贯穿始终的设计准则是：**用确定性代码兜住流程，把 LLM 用在刀刃上，时刻盯紧成本与延迟。**

## 八、最小可运行代码骨架（Python + Anthropic SDK）

下面用一份**能直接跑**的最小代码，把前面所有概念落到地上：**编排器 + 两个 Agent + 一个工具 + 共享记忆**。各部分严格对应正文术语，注释里标了出来。

> 设计取舍（呼应正文）：
> - **编排逻辑用确定性代码**（普通的函数调用顺序），不交给 LLM 当调度器 —— 见第二节"工程关键"。
> - **搜索 Agent 用"手写 agentic loop"**（自己控制循环），因为它要调用工具，需要看到每一步;**写作 Agent 是单次 LLM 调用**,不需要循环 —— 呼应误区 1"不是所有 Agent 都要复杂调用"。
> - 工具（`web_search`）这里是**桩函数**（mock），真实场景换成联网搜索 / RAG 检索即可。

### 1. 共享记忆 + 工具定义

```python
import json
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-opus-4-8"  # 当前最强 Opus；简单子任务可换 claude-haiku-4-5 省算力

# ── 上下文记忆层：全局共享记忆（所有 Agent 可读写）──────────────
class SharedMemory:
    """对应正文"全局记忆"。真实系统里这层往往落到 RAG 向量库 / DB。"""
    def __init__(self):
        self.store: dict[str, str] = {}

    def write(self, key: str, value: str) -> None:
        self.store[key] = value            # 增量写入，不整体覆盖

    def read(self, key: str) -> str:
        return self.store.get(key, "")

# ── 工具层：一个工具的 schema + 它的本地实现 ────────────────────
SEARCH_TOOL = {
    "name": "web_search",
    "description": "联网搜索最新资料。当需要训练数据之外的实时信息时调用。",
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {"type": "string", "description": "搜索关键词"}
        },
        "required": ["query"],
    },
}

def run_web_search(query: str) -> str:
    """桩实现：真实场景替换为搜索 API 或 RAG 检索。"""
    return f"[模拟检索结果] 关于「{query}」的 3 条要点：1) ... 2) ... 3) ..."
```
