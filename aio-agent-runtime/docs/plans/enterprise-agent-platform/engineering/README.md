# 工程契约层：把阶段计划落实到可审查实现

> 文档状态：设计草案，全部待实现/待验证。当前业务代码未因本轮规划发生修改。SQL、JSON、状态和时间示例用于定义契约，不是可直接套用的生产配置。  
> 本层继续使用原有 110 个父任务、718 个子任务，不用增加任务数量替代工程深度。

## 1. 这一层解决什么问题

上一级回答“做哪些任务、依赖谁、在哪个阶段验收”。本层回答：

- 谁是权威事实源，字段到底从哪里产生？
- 数据库事务怎样开始/提交，加锁顺序是什么？
- 两个请求竞争、权限变化、进程崩溃时，哪种结果才正确？
- 审批批准的究竟是哪份代码、哪批输入、哪个外部账号？
- 用户代码和持有凭据的连接器是否真的隔离？
- 如何用夹具、计数器和故障点证明没有重复写或越权？
- 一个子任务提交 PR 时需要带哪些设计、迁移、测试和回滚证据？

本层不是全部实现已经可以无脑生成的承诺。企业 SSO、Secret 服务、运行时兼容、存储硬配额、外部写系统能力仍要通过 G0/对应 PoC 确认。

## 3. 设计优先级与冲突处理

1. 对用户明确授权、公司正式数据政策、批准的安全边界必须遵守，不因计划示例放宽。
2. 本层的显式澄清修正上层模糊处：例如一个 Run 可以有多个不同权限的执行 cell，而不是所有代码与凭据共用一个容器。
3. 总计划 03/04/05 与阶段手册仍用于范围、角色、任务/阶段关系；本层用于事务/协议/失败判定细节。
4. 若实现需要改变这里的决策，应先记录 ADR、修改调用方契约和负例，再进入开发，不能两个模块分别采用相反默认值。
5. 行号只是当前位置，引用以稳定任务 ID、INV/TX/ECASE ID 和文件路径为准。

## 4. 子任务准备、完成和开放的不同证明

| 状态 | 必须有的东西 | 不等同于 |
|---|---|---|
| ready_to_start | 已批准输入契约、依赖就绪、具体写入范围、至少一个正例和一个拒绝/失败例 | 实现已完成 |
| implemented | 代码、迁移、契约和测试写出；无未说明旁路 | 测试已通过 |
| verified | 真实指定环境上执行，产出 commit/image/config/样本/原始断言结果 | 生产允许开放 |
| releasable | 对应 Gate、数据/用户/工具/profile 范围签字，恢复和应急已验证 | 任意用户和能力都允许 |

本轮所有工程任务仍 `not_started`。当前提交文档只表明规划更明确，不能为业务任务勾选完成。

## 5. 新澄清的几个重要限制

- RLS 的 `app.org_id` 由可信应用设置，只能防遗漏 scope 等错误；拿到任意 SQL/应用 DB 凭据的攻击者可能自行设置它。因此不把该机制当 SQL 注入或数据库凭据失陷的独立安全边界。
- 控制帧和 stdout 分流只能防直接文本伪造路径；若 runner 与用户代码同 UID/权限，不应信任 runner 的安全声明。可信退出/销毁/配额/发布由外部 manager/collector 验证。
- 持有业务凭据的 stdio MCP 默认使用独立 connector cell，计算 cell 不能读它的 Secret 或绕过工具网关直接使用凭据。
- 用户撤权提交后，新授权决定必须拒绝；已经进入网络缓冲、已下载、已被外部服务接受的内容无法被“立即撤回”。计划定义可测试的边界，不承诺分布式零延迟取消。
- `recovery_required` 不是普通失败。它停止执行，却保留待核对的占用/阻断范围，不允许悄悄释放所有业务约束再重跑。
- 真实业务副作用不能包进数据库事务；工具授权/意图/派发/结果分步骤持久化，并明确不确定窗口。

## 6. 推荐使用方式

BE-A 先阅读 02/03；BE-B 先读 03/04/06；PE 先读 04/05/09；FE 先读 07；QA 从 01/08 开始并参与每次契约变更。所有角色共同遵守 01 的不变量。

领取任务时从验收绑定找到主契约与基线测试，再补该具体改动的专属断言和交付物。绑定中的测试只是最低相关集合，不能因为“已有基线测试通过”就省掉新增逻辑的验证。
