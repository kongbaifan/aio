# 阶段执行手册：从总体计划到可领取任务

> 状态：全部待实施。细化基线为上一级 01–07 文档和原有 110 个父任务；本目录只增加执行规划，不表示已写出接口、迁移或自动化测试。  
> `P0–P6` 表示交付阶段；上级文档测试表中的 `P0/P1` 表示风险优先级，二者不要混淆。

## 1. 使用方法

1. 先看本页的开放边界和依赖原则，再进入对应阶段文件。
2. 每个父任务保留原 ID，子任务使用 `父ID.序号`，例如 `RUN-08.03`；不要再创建第二个同义任务。
3. 负责人、原始依赖及阶段归属见 [任务索引](task-index.md)，父任务定义见 [06 实施总表](../06-work-breakdown-and-roadmap.md)。阶段正文负责更细的改动、契约、步骤、证据和回滚。
4. 每次只领取一个可验证的小切片。改 schema、授权、执行器的 PR 必须同时含对应负例，不先留一个宽松实现以后再补安全。
5. 子任务勾选需关联 PR/commit、测试报告和审查记录。规划文件生成、接口 stub、假模型演示都不等于业务任务完成。
6. 本文提到的新文件、命令、API、测试路径都是拟实现位置；当前不存在的验证脚本不能直接当作现成命令运行。

## 3. 这次细化对原阶段顺序的澄清

原总表按功能分组，不能简单按表从上往下串行开发。以下基础必须前移：

- `GOV-01/02/04/07` 的数据策略、持久审计、应急禁止和模型配置安全，在 P2 开放任何执行路径前可用，而不是等 P5。
- `CAP-01/02/07` 的工具网关、最小版本化 Manifest 与旧入口封闭属于 P2，完整 Skill/Agent 管理属于 P3。
- `RUN-10` 在 P2 完成最小预算准入；`GOV-03` 在 P4 完成全部结算、价格版本和运营界面，不能先无预算调用真实付费模型。
- `IAM-09` 在 P1 定义支持访问授权；真正诊断包和 UI 在 P4 集成。先有权限边界，后有管理体验。
- `OPS-01/02` 在 P2 提供可信镜像和安全环境配置；`OPS-03` 在 P4 做联合恢复验收。任何更早发生的持久数据变更仍必须先有局部备份和回滚记录。
- P3 可以实现和用合成数据验证 stdio MCP/外部写，但不因代码已合并就向试点员工开放。真实外部写在 P5 按工具逐一准入。
- P5 不是等到这时才做所有治理，而是以已经验证的能力为基础完成 HA、应急、升级、运行支持和正式放行。

这是依赖关系的细化，不删除原 110 项，也不把同一工作重复计算人力。

## 4. 三种完成程度，必须分开记录

| 程度 | 可以声明什么 | 不可以声明什么 |
|---|---|---|
| 接口就绪 | schema/契约已冻结，fake 可让另一组联调 | 真业务、安全、故障恢复已经完成 |
| 集成完成 | 真实依赖上的适用用例通过，有固定版本证据 | 所有用户/数据级别/执行器都获准使用 |
| 开放获批 | 对应 Gate 和能力画像通过，配置已限定范围 | 能力可以无限扩量、增加权限或更换运行时 |

父任务的依赖表示最低接口/数据前置；同一阶段内还需遵守正文的联调顺序。跨阶段只能拿已通过的明确接口契约继续开发，不能跳过安全放行。原最低依赖没有列出不代表可省略全局身份、数据策略和审计。

## 5. 统一实施约束

### 5.1 路径缩写

- `APP/` = `aio-agent-runtime/apps/local-harness/app/`
- `HTEST/` = `aio-agent-runtime/apps/local-harness/tests/`
- `MIG/` = `aio-agent-runtime/apps/local-harness/migrations/`
- `SM/` = `aio-agent-runtime/services/sandbox-manager/src/sandbox_manager/`
- `EX/` = `aio-agent-runtime/services/run-executor/src/run_executor/`
- `WEB/` = `aio-agent-runtime/web/platform/src/`
- `INFRA/` = `aio-agent-runtime/infra/`
- `SCRIPT/` = `aio-agent-runtime/scripts/platform/`
- `DOC/` = `aio-agent-runtime/docs/`
- 工作流仍写在真正仓库根 `.github/workflows/`，不是在子项目再创建一个失效位置。

除明确标“当前文件”外，新路径按任务创建；不要复制根目录归档来同时维护另一份业务入口。

### 5.2 通用输入契约

- 身份来自验证过的 Principal，不来自 JSON body 中自报的 user/org。
- 数据库事务设置上下文并清理，所有租户外键同 org；RLS 与业务动作授权同时存在。
- 工作区、沙箱、连接、镜像、模型与 Secret 只能用平台验证过的引用，不接受用户任意系统路径或 endpoint。
- 外部副作用前持久记录意图；网络错误不等于外部没有执行。
- 旧 Worker/generation 不能执行新动作；无法撤销已发出的远端请求，必须核对。
- 规划中的 JSON/YAML 示例只是字段约定，不能直接用作已验证的生产配置。

### 5.3 PR 和验收记录

每个 PR 至少填写：父/子任务 ID、依赖版本、文件范围、迁移影响、接口/事件变化、正负测试、数据/执行风险、功能开关默认值、回滚/补偿、未完成项。

推荐单 PR 聚焦一个可验证边界。某子任务预估超过两个工作日，领取时继续拆成 `.a/.b` 工程清单或多个 PR，但保留父子 ID 追踪；不要为了凑两天删负例。

受控证据建议存放在 `var/verification/<release>/<task-id>/` 或公司测试平台，不把原始业务数据和 Secret 提交进文档仓库。每份记录包含 commit、镜像 digest、kernel/runtime、配置摘要、样本版本、命令、exit code、passed/failed/skipped 和审查人。

### 5.4 任务状态

`not_started → contract_ready → implementing → verifying → reviewed → accepted`；环境/外部依赖阻塞可标 `blocked` 并写可解除条件。`accepted` 仍不等于能力可以生产开放。

本轮所有任务保持 `not_started`。此状态规范不是要求调用会话工具创建或完成任何 Goal。

## 6. 环境与开放矩阵

| 阶段结束 | 允许的环境和数据 | 可开放 | 必须关闭 |
|---|---|---|---|
| P0 | 本地/隔离 CI，合成样本 | 文档、基线、fake 演示 | 多人真实业务、任意执行 |
| P1 | 隔离平台，两组织测试身份 | SSO/私有资源 CRUD | 任意代码、共享全局 Token 路径 |
| P2 | 专用 Linux 测试执行节点，合成数据 | 已通过 profile 的执行集成测试 | 对员工的未验收执行、真实业务写 |
| P3 | 预发布，获批准脱敏样本 | Skill/MCP/KB 联调与安全验证 | 任意第三方发布、未经批准外部写 |
| P4 | 限部门白名单、限定数据类型 | 已批准 Agent/Skill、只读 MCP、ACL KB、受限计算 | 广域写、任意出网、未验证 profile |
| P5 | 经签字批准的生产范围 | 逐项准入能力、按设施水平提供服务 | 没有证据的高危能力、共享 root/管理员凭据 |
| P6 | 独立实验环境开始 | 通过单独验收后灰度新增能力 | 绕过旧权限/预算/审计或引擎自动替换 |

## 7. Gate 证据组织

- P0 对应 G0；P1 对应 G1。
- P2 对应 G2/G3 的基础闭环，后续新增执行器/传输仍需补其专属证据。
- P3 对应 G4。
- P4 对应 G5，包含受限试点 UAT、备份恢复和回滚预演。
- P5 对应 G6，基于实际 HA/支持能力定义服务承诺。
- P6 不继承其他引擎或连接器的安全通过结论，要重新跑相关 Gate 的差量和共用回归。

测试编号沿用 [07 测试矩阵](../07-verification-operations-rollout.md)。新增场景可以补充，但不能让原负例因接口重构而悄悄消失。

## 8. 领取顺序与跨组交接

1. PM/SEC 冻结 G0 的业务样本和禁止项。
2. BE-A 完成身份/资源/数据库最小契约，BE-B 和 PE 只用 fake 开发下游接口。
3. BE-B 提供 Run/lease/event 契约，PE 提供 manager/executor 私有协议；交叉评审后集成。
4. FE 使用同一 OpenAPI/事件类型，不能手写另一套状态含义；无后端功能时显示不可用，而非假成功。
5. QA 从 P0 开始建立权限和故障夹具，阶段尾只收敛，不临时补全测试策略。
6. 所有新增执行路径都由 PE/SEC 审查，所有新增业务资源都由 BE-A/SEC 审查；改一侧必须通知另一侧。
7. 先完成一个获权分析任务的全链路，再扩更多 Skill、MCP 和知识来源。

## 9. 工期口径

沿用总计划的 12–16 周受限试点、16–24 周完整第一版参考窗口，前提仍是对应人员、设施和少量连接器。子任务细化没有制造新的工期保证。

每阶段 kickoff 应把任务按团队实际速度做三点估计，区分工程投入、评审等待、外部系统接入和压测/演练时间。重叠阶段不重复计算父任务；任务索引的 home stage 表示详细定义归属，不代表所有子任务只能在那一周开始。

## 10. 进一步的工程契约

阶段任务领取后，使用 [工程契约层](../engineering/README.md) 和 [验收绑定](../engineering/acceptance-index.md) 明确事务、字段、锁序、错误/恢复、可信执行边界、前端事件和证据。原 718 个子任务不新增数量；补充的工程测试是后续联调/放行义务，不把后期集成测试反向变成早期 schema 开工依赖。

尤其注意新澄清：credentialed connector 与任意代码分 cell；GUC RLS 不抵御持应用 DB 凭据的任意 SQL；沙箱自报状态不作为管理事实；recovery_required 保留必要业务阻断。这些边界以工程契约的显式定义为准。
