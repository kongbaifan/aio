# 子任务依赖、联调顺序与开放门禁

> 本页细化 110 个父任务内部的调度约束，不增加父任务数量。所有条目仍待实施。阶段手册是工作内容依据，原 06 表是负责人/最低父依赖依据；此页明确最易被误读的契约分界。

## 1. 三种依赖不能混为一谈

1. **开工依赖**：所依赖数据/接口足以开始该子任务，可以使用契约一致的 fake 做局部开发。
2. **集成依赖**：真实实现和对应负例通过，才允许将子任务标为验收完成。
3. **开放门禁**：全部适用安全/业务/运维证据通过后，才允许向某用户/数据范围开放功能。

以下列表给出可保守执行的顺序：同一卡默认按子序号推进；没有特别拆分的原父依赖，调度时先完成前置父卡。未来可以按明确契约进一步并行，但不得省略集成验收。所有依赖只有在记录的 PR/证据完成后才算满足。

## 2. 两处必须拆开的契约依赖

如果把原父依赖机械理解成“整张卡必须完成才能开始另一张卡”，会在细化后产生预算/Manifest 的隐性循环。用以下契约里程碑解除，不降低最终验收标准。

| 后继父任务 | 原前置父任务 | 可先采用的前置子任务 | 最终闭环 |
|---|---|---|---|
| RUN-10 | RUN-02 | RUN-02.01 | Run 请求/资源契约先定，预算预留实现后才完成 Run 创建事务；RUN-12/GOV-03 联合验收 |
| CAP-02 | CAP-01 | CAP-01.01 | 先定无身份工具定义，再建 Manifest，随后 Gateway 使用 Snapshot 重新授权；CAP-07/G4 验收 |

关键顺序：

```text
RUN-02.01（创建输入契约）
    → RUN-10.01/02（预算语义与事务预留）
    → RUN-02.04（Run + Job + 预算原子创建）

CAP-01.01（无身份工具定义）
    → CAP-02.01/02/03（能力版本、解析、Snapshot）
    → CAP-01.03（按 Snapshot + 当前权限裁剪执行）
    → CAP-02.05（撤权与 Snapshot 上限联调）
```

两张父卡最终仍必须完整验收；不是取消预算或 Manifest 的强制性，也不允许 production 先用“总是允许”的 stub。

## 4. 必须单独记录的开放条件

| 能力 | 代码可能何时准备好 | 真正开放还需什么 |
|---|---|---|
| 代码执行 | P2 | 对应 executor/profile 的 G2、Run G3、G5 用户/数据批准 |
| browser/parser/stdio | 各 adapter 合并时 | 每条新增路径自己的网络/凭据/资源/清理差量，不继承 Python 结果 |
| 项目/产物分享 | UI-05 提供关闭态，P4 服务集成 | GOV-06、派生来源/即时撤回语义和双用户验证 |
| 外部业务写 | MCP-06 合成测试通过 | 实际工具幂等/查询、外部账号权限、审批人/补偿责任与 P5 准入 |
| 运维查看正文 | IAM-09/GOV-05/UI-08 | 当前 Run 限时 support grant，强认证/字段范围/访问审计 |
| HA 服务承诺 | 可以早部署多副本 | OPS-06 实际故障域/容量/恢复证据，不以 Pod 数量代替 |
| 自定义 Skill | 可以上传草稿 | 扫描、隔离测试、审核、版本和资源授权，不可自动发布执行 |
| Codex 候选 | ENG-02 可运行 | ENG-03/04/05 和当前固定版本官方支持/条款/安全结论 |

## 5. 不应该用来解除依赖的方法

- 用允许所有权限的 PolicyService stub 推进真实用户测试。
- 用共享 SandboxClient 让 UI 先“能跑”，后续再改隔离。
- 用内存审批/事件证明重启恢复。
- 在没有硬配额的 named volume 上声称磁盘限制通过。
- 将准备好的前端按钮当作对应后端已安全实现。
- 将 prototype/mock 的接口就绪当作生产能力验收。

未就绪可以继续使用合成数据和契约一致的 fake 开发下游，但状态只记 contract_ready；任何演示/报告必须明确是假依赖还是实测。
