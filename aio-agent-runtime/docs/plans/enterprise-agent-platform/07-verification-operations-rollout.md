# 07. 验证、运维、迁移、灰度与生产放行

> 本文件是测试/发布计划，不是测试报告。以下场景本轮均未执行。测试必须针对将要部署的镜像、内核、运行时、网络策略和数据库角色实施。

## 1. 测试分层与环境

| 层级 | 内容 | 环境 | 不能证明什么 |
|---|---|---|---|
| L0 静态/单元 | schema、策略、状态机、路径校验、脱敏、fake engine | 普通 CI，无真实 Secret/业务写 | 不能证明 OS 隔离 |
| L1 服务集成 | PG/RLS/对象存储/job/outbox/审批/SSE | 隔离测试服务与真实依赖 | 不等于真实容器和网络已安全 |
| L2 执行隔离 | 实际镜像/manager/执行器/限额/出网/清理 | 专用 Linux 测试执行节点 | 不能穷尽内核未知漏洞 |
| L3 浏览器端到端 | SSO 测试身份、双用户、审批、文件、重连 | 隔离平台环境，真实浏览器 | 不能只以按钮隐藏作为授权验证 |
| L4 故障与性能 | 断网、重启、旧 Worker、磁盘压力、负载 | 与生产等价但无生产数据的环境 | 结果不能直接推广到更大硬件/数据规模 |
| L5 安全/业务验收 | 滥用测试、权限审查、业务正确性、运行手册 | 限定范围的预发布环境 | 不能用功能演示代替安全测试 |

资源耗尽/进程树/恶意文件测试只在可销毁节点、严格外层配额与无生产网络条件下运行。不要在共享开发服务器、当前用户机器或生产节点直接跑压力/逃逸试验。

## 2. 基础测试夹具

- Org-A、Org-B；Org-A 下财务、销售、HR 三组。
- Alice（销售）、Bob（财务）、Carol（跨部门）、DisabledUser（停用）、Operator（仅运维）、Auditor（审计）、Approver（特定业务写审批）。
- 两个个人项目、一个明确共享项目、一个同名但跨 Org 项目。
- 两个不同身份的 MCP 测试账号；独立 read-only、支持幂等 write、无幂等/结果不明服务。
- 两用户同名文件、带 Unicode/特殊字符文件名、损坏文档、恶意归档、伪造 MIME、限额边界样本。
- 一组明确允许/禁止访问的知识文档，包含同名文档和不同版本。
- fake 模型可固定输出“越权工具参数”，用于证明即使模型试图调用也被服务器拒绝。
- 独立假 SSO issuer、假 Secret 服务、模拟 401/429/超时/重复消息/连接中断的代理。
- 全部夹具可重复创建和删除，测试资源标签与生命周期明确，不写真实业务系统。

## 5. CI 与验证流水线

### 5.1 每个 PR

1. Secret 扫描、依赖和配置静态校验、类型/lint。
2. 保留现有 Harness/Sandbox/前端回归；新平台单元/状态/策略测试。
3. PG 集成、RLS、迁移、API/事件 schema 兼容性测试。
4. 新前端 unit/component，关键双用户 browser smoke。
5. 生成 OpenAPI/TypeScript 类型并检查漂移。
6. 构建应用与执行镜像的可复现摘要；普通 PR 不使用生产凭据。

### 5.2 执行器/网络/依赖变更

- 在专用可销毁 Linux runner 上执行 L2，包含当前全部执行器。
- 使用实际运行时配置验证 cgroup、磁盘、网络、PID、进程树、清理和无旁路。
- 自托管/具备 Docker 管理能力的 runner 不执行未经信任的外部 PR 且带生产 Secret；与生产网络隔离。
- SBOM、漏洞/许可证、签名和模板准入检查。
- 浏览器/原生包升级必须重复兼容与安全 profile 测试，不能只跑 Python 单元测试。

### 5.3 发版前

- 全套适用 P0、业务 UAT、负载与恢复演练、镜像签名、依赖和漏洞例外审核。
- 用例失败时要么修复，要么关闭对应能力并验证无法调用；不以“已知问题”覆盖核心隔离风险。
- 覆盖率是辅助指标；核心授权分支与状态转移的正负例必须明确映射，不能凭 90% 行覆盖率宣称安全。

## 6. 性能、容量与费用验证

### 6.1 工作负载组合

- 40% 授权 KB 问答/只读 MCP，通常不创建代码沙箱。
- 40% standard 表格/脚本任务。
- 20% browser 或较重文档任务；比例只是初始压测假设。
- parser 摄取作为独立低优先级负载，验证不挤占交互任务。
- 模型可用模拟服务测平台开销，再用获批准的真实模型做小规模业务压测，费用单独批准和设限。

### 6.2 负载阶段

1. 单用户单 Run：测平台、模型、工具、沙箱启动分解耗时。
2. 2/5/10 并发逐级提升，每级至少稳定运行 30 min；执行单元不突破 profile/节点配额。
3. 队列超额提交：验证公平性、排队解释、429/取消和预算预留。
4. 2 h 目标峰值运行，检查 DB/对象存储/磁盘/连接池和后台清理。
5. 24 h 长稳，观察内存、线程、FD、容器、卷、Node Worker、浏览器 Profile、对象孤儿是否持续增长。
6. 温/冷镜像、网络限速、上游 429、慢 SSE 消费者分别测试。

### 6.3 记录的指标

平台 API P50/P95/P99、排队时间、沙箱 ready 时间、工具耗时、事件延迟、Run 完成率、取消收敛、资源利用率、清理失败、未知外部效果、unknown usage、每业务任务模型成本估计。

不要只记录“每秒请求数”。业务并发取决于 Run 持续时间与工具组合；100 名用户不等于 100 个永久容器。用试点数据反推节点数量和镜像预热池规模。

### 6.4 费用治理验证

- 组织/部门/用户/Run 的预算预留与实际消耗分开显示。
- 多轮推理、planner、summary、embedding、reranker 都入账。
- 上游 usage 不可靠时使用明确的估算/unknown 标记；结算后以可核对账单修正。
- 试点设置日预算与单 Run 预算，不用静态模型轮数代替费用控制。
- 未给出人民币/美元承诺，因为供应商价格、模型与任务分布尚未确认。

## 7. 监控与告警

### 7.1 建议指标

- `api_request_duration_seconds{route,status}`
- `run_queue_wait_seconds{queue}` / `run_active{state,engine}`
- `tool_duration_seconds{tool_kind,outcome}`
- `sandbox_active{profile,state}` / `sandbox_provision_seconds{profile}`
- `sandbox_cleanup_failures_total{reason}` / `sandbox_orphans`
- `node_disk_free_bytes`、inode、内存压力、CPU、PID/FD 使用
- `approval_pending` / `approval_expired_total`
- `policy_denied_total{action,reason}`
- `audit_outbox_backlog` / oldest age
- `model_usage_unknown_total{provider}` / budget reservation backlog
- `knowledge_ingest_failures_total{stage}` / deletion backlog

Metric 标签不用 user_id、run_id、完整 URL、文件名、prompt 或 Secret，防高基数和隐私泄露。关联 run_id 进入有访问控制的日志/trace 元数据。

### 7.2 起始告警阈值示例

- 任意跨租户测试/真实越权信号：立即安全告警，停止受影响能力。
- 连续沙箱清理失败、出现超期孤儿或不能确认停止：隔离节点，禁止新调度。
- 审计 Outbox 持续积压或高风险审计不可写：禁止新增高风险动作。
- 队列等待长期超过业务阈值、执行节点不足：告警但不解除配额。
- 磁盘/内存余量低于准入水位：暂停分配，清理已到期资源。
- unknown 外部写/usage 突增、预算异常：业务和运维共同核对。

阈值须用真实基线确定。告警发给有处置责任的人，不只放一张仪表盘。

## 8. 事故处置 Runbook

### 8.1 沙箱疑似被污染或突破边界

1. 禁用受影响 Run/Skill/镜像/节点的新执行；撤销相关短期能力与连接。
2. 停止网络，隔离节点，不把其现存容器或卷回池。
3. 保全必要且获授权的审计、镜像 digest、节点/运行时版本、调用链；不要把含密钥内存/磁盘直接发送到公共工具。
4. 评估接触过的凭据和业务系统，按最小范围轮换并扩大排查。
5. 从可信镜像/节点重新部署，复跑相关安全 suite 后恢复。
6. 记录根因、影响、通知和预防项；不能只删除 workspace 后继续使用。

### 8.2 任务卡住或 Worker 丢失

1. 根据 run_id 查 state、lease、generation、最后事件、Invocation 状态。
2. 确认是排队、模型等待、审批、执行、持久化还是清理。
3. 若有 executing 外部写，不直接点重试；先查询外部结果。
4. 撤销旧 generation，manager 停止/隔离旧执行单元。
5. 符合安全重试策略时创建关联新 Run；否则交业务审批人核对。

### 8.3 凭据泄漏

1. 立即撤销/轮换 binding，并关闭对应连接池与 capability。
2. 找出关联 Run、工具、日志、Artifact、用户访问记录。
3. 阻止泄漏内容继续分发；按保留要求隔离取证，不直接销毁所有证据。
4. 检查上游系统已产生的调用；通知安全/业务负责人。
5. 增加泄漏源的字段级脱敏与权限测试，而不是只增加一个字符串正则。

### 8.4 知识库越权/错误引用

1. 禁用受影响 KB/文档/检索缓存，停止关联新调用。
2. 查来源 ACL、索引版本、缓存 scope、上下文 provenance。
3. 修复权限/索引，重建必要摘要；已披露内容按事件响应处理。
4. 重跑 KBTEST-03..09/13/14 和相关业务样本，确认后恢复。

### 8.5 磁盘满/资源紧张

1. 停止新沙箱分配，保留控制服务和状态持久化余量。
2. 清理已确认到期的临时卷/镜像缓存/孤儿对象；不要递归删除计算出来但未验证的活跃目录。
3. 排查输出洪水、镜像拉取、失败保留副本和 inode 压力。
4. 调整配额/准入，不用取消限制让更多任务挤入。

## 9. 备份与恢复

### 9.1 备份集合

- PostgreSQL 基础备份 + WAL/PITR，包含权限、Run/审批、账本、Artifact 引用与删除记录。
- 对象存储版本/快照、已发布 Skill 包、WorkspaceVersion、原始知识文档及产物。
- 镜像 digest、部署配置、网络/profile 策略、Agent/模型配置版本。
- Secret 服务/KMS 的恢复依赖与操作程序；不把明文密钥放普通备份包。
- 重要撤权/删除/禁用事实与安全审计要有独立受控保留，恢复时可核对。

### 9.2 恢复顺序

1. 在隔离网络创建恢复环境，默认不出网、不执行任务、不开放用户登录。
2. 恢复 DB、对象存储和配置；核对引用完整性与校验和。
3. 恢复 Secret 服务引用，验证当前版本；不自动启用旧 Token。
4. 从权威身份/数据源同步当前停用/撤权/删除状态，并重放独立记录。无法确认的资源保持拒绝，不依据旧备份默认为公开。
5. 所有历史 active Run 先进入待核对；不要恢复后自动重跑外部写步骤。
6. 重建/核对搜索索引，验证 ACL 与文档版本。
7. 双用户授权、下载、只读任务、预算、审计与恢复测试通过后小流量放行。
8. 记录实际恢复点、数据缺口和耗时；与 RPO 15 min/RTO 4 h 的初始目标对比。

每次大迁移/存储方案变化后演练，常规至少按公司策略定期验证；建议月度抽样、季度全链路恢复。备份“任务成功”不等于数据真能恢复。

## 10. 当前项目迁移到平台版

### 10.1 准备

- 不直接修改原有 SQLite 和共享 workspace；先获取一致备份与来源清单。
- SQLite 正在写入/WAL 模式时用在线备份 API 或停写后的完整一致快照，不能只复制主 `.sqlite` 文件。
- 管理员提供 legacy session/file→org/user/project 映射，无映射项隔离。
- 梳理 Skill 来源与版本；模型配置转换为受控配置与 SecretRef，不能复制用户 Shell 密钥解析逻辑。

### 10.2 迁移工具必须有的模式

- `inventory`：只读列出记录/文件/hash/类型/潜在敏感项，不输出 Secret 正文。
- `dry-run`：验证映射、目标约束、冲突和预期计数，不写生产。
- `import`：按批事务写入，以 source+legacy_id 保证幂等。
- `verify`：数量、内容 hash、归属、时间、模型标签、Artifact 引用和 ACL 核对。
- `report`：生成成功/跳过/冲突/无主清单，人工签字。

以上是拟实现的命令模式，不是当前仓库已有 CLI。

### 10.3 切换步骤

1. 完成预演、备份恢复与权限检查，锁定迁移版本。
2. 将旧服务停止写入/仅本地受限访问，禁止继续产生新执行数据。
3. 执行最终一致快照、增量迁移与 verify。
4. 新平台只向白名单开放，旧全局 Token 不进入新认证域。
5. 首先只读验收会话和产物，再开放低风险 Run。
6. 未映射旧数据保留受限，不因“大家以前共用”而自动共享。
7. 确认稳定后按留存政策归档旧服务；不是本轮直接删除目录或数据库。

### 10.4 回滚边界

迁移后产生的新账本、审批、权限和任务记录不能通过恢复旧快照丢掉。优先回滚应用代码/能力版本，保留向后兼容 schema。若需要数据级回退，进入维护窗口，由负责人依据明确备份与数据合并方案执行，不自动 `downgrade` 删除表。

## 11. 发布与灰度

### 11.1 发布前检查

- 已通过对应 G0–G5，所有 P0 和已启用能力测试有证据。
- prod 配置拒绝匿名、默认 Token、旧开发路由、控制侧任意命令、任意 endpoint。
- 镜像 digest/签名/漏洞例外、schema 兼容、Secret/证书有效期、备份可恢复。
- 数据库迁移由单独受控 job 执行，不能多个 API Worker 启动时争抢改 schema。
- API 与 Worker 滚动升级支持当前 Run/event schema；旧 Worker 先停止领取新任务并排空。
- 非幂等远端工具不可用自动重试兜底。

### 11.2 灰度阶梯示例

1. 开发/测试人员 + 合成数据，全部误用/恢复用例。
2. 约 10 名业务种子用户，限定三类任务、只读或沙箱内写、明确低敏数据。
3. 每部门少量员工，总计约 30–50 人，按指标逐步提高并发和能力。
4. 完整生产首版放行后扩至目标员工，仍保留部门/能力/模型开关。

用户数量是示例，不是自动扩量计划。每次扩量观察错误率、队列、unknown 写、费用、审计和资源清理；触发阈值停止扩量或禁用对应能力。

### 11.3 回滚流程

- 先停新 Run/禁用问题能力，保留正在执行任务的可核对状态。
- 将新请求切回已验证的应用/Agent/Skill/镜像版本。
- 对执行中任务按版本继续排空或明确取消；不把旧 generation 悄悄接到新容器。
- 保留 PG/对象存储新记录；按 expand-contract 兼容窗口运行。
- 对已经发生的外部写，只能业务核对/补偿，不把“回滚平台版本”说成已撤销业务操作。
- 记录回滚原因、受影响 Run 和恢复门槛。

## 13. Definition of Done

“企业多部门平台第一版完成”至少意味着：

- 员工在网页完成首批业务旅程，管理员能配置能力并按权限治理。
- 其他用户的会话、文件、知识、连接和执行环境无法通过已定义路径访问。
- 执行器全部处于可验证的隔离与资源边界，没有 shared-host fallback。
- 任务、审批、事件、预算与产物在重启/重复/断线情况下语义明确。
- 所有开放 Skill/MCP/知识库有版本、权限、凭据边界、撤销机制与测试。
- 运维能看到问题、得到告警、申请排障权限、恢复备份、回滚版本并处置未知业务写结果。
- 不支持/未验证的能力明确关闭；遗留风险有负责人、限制措施和截止时间。
- 本目录的计划项转为真实 PR、自动化测试和放行证据，而不是仅保持一张漂亮架构图。

## 14. 风险登记与降级边界

| 风险 | 影响/早期信号 | 负责人 | 处理与不允许的降级 |
|---|---|---|---|
| RISK-01 权限只加在部分 API | 直接下载/SSE/管理测试可绕过 | BE-A/SEC | 全路径矩阵；未通过不开放多用户，不靠隐藏按钮补救 |
| RISK-02 执行节点不支持硬磁盘/网络限制 | profile 有配置但真实测试失败 | PE/SEC | 更换存储/运行时或降低开放能力；不能以定期清理代替 |
| RISK-03 第三方 MCP 不支持幂等/结果查询 | 超时后无法判断是否已写入 | BE-B/业务 | 只读接入或禁止高风险动作，不做盲目自动重试 |
| RISK-04 外部模型/嵌入服务不符合数据政策 | 采购、地域、条款或审计要求不满足 | PM/SEC | 选合规端点/部署；不能为了效果偷偷换 Provider |
| RISK-05 自定义 Skill 来源与依赖不可控 | 可执行包未经审查、运行时下载无固定版本 | 能力维护者/SEC | 隔离测试、来源/锁依赖审查；默认不能发布到组织 |
| RISK-06 人员与工期低于计划 | 只有 1–2 人，仍要求所有连接器/HA/任意代码 | PM/ARCH | 缩减业务范围/连接器数量或延长期限，不减授权与隔离 |
| RISK-07 归档组件来源/许可证不清 | 缺原始仓库、构建链或授权证据 | SEC/法务/PE | 排除该组件或替换已获准依赖，不假定提取物可商用 |
| RISK-08 进程状态无法恢复 | Node/浏览器内存依赖、模型流中断 | BE-B/PE | 明示不可恢复并新建 Run；不伪造透明恢复和成功 |
| RISK-09 运维设施不足以支撑 HA/RPO | 单机部署、未验证备份、缺值班 | PE/PM | 保持试点服务等级，先补恢复能力；不承诺 99.9% |
| RISK-10 Codex 协议/实验接口变化 | schema/认证/内置工具行为改变 | ARCH/BE-B | 固定版本、独立 PoC、关闭候选引擎，不阻塞 V1 |
| RISK-11 衍生产物权限比来源宽 | 受限数据被重新生成后公开分享 | BE-A/SEC | 来源与标签传播、分享校验/审批；不能凭模型自称脱敏放行 |
| RISK-12 预算/审计事实不完整 | unknown usage、大量 Outbox 堵塞、丢意图 | BE-B/PE | 限制新计费/高风险动作并对账；不把未知当零或无副作用 |

每个真实风险补充：发现日期、受影响版本、缓解措施、验证证据、剩余影响、接受人和期限。P0 只能修复或关闭对应能力，不能仅写入风险登记后继续开放。
