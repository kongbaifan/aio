# 04. 沙箱、权限、凭据与数据安全设计

> 工程层补充：实现时同时阅读 [工程契约索引](engineering/README.md)。其中明确了多权限 cell、RLS 威胁边界、事务锁序、审批与未知效果、当前撤权和可信资源核对；不把本页架构概览当作已实现保证。

> 目标是降低并限制不可信执行的影响范围，而不是声称任何容器/微 VM 绝对安全。系统隔离、业务授权、资源治理和数据治理分别设计、分别验收。

## 1. 威胁模型

### 1.1 需要保护的资产

宿主机与控制服务、其他员工数据、业务系统账号、模型与云密钥、知识文档、公司网络、预算、审计记录、已发布 Skill/镜像、任务与审批完整性。

### 1.2 不可信输入

- 员工自然语言、上传文件、自定义 Skill、项目代码、包依赖及安装脚本。
- 模型输出的命令、路径、URL、参数、工具名与“建议权限”。
- MCP 的工具描述、返回值、资源链接和远端内容。
- 浏览器网页、PDF/Office 文档、图片/OCR 内容和 Git 仓库。
- 即使维护者是内部员工，也假设误操作、账号失窃和供应链污染可能发生。

### 1.3 威胁与控制矩阵

| 威胁 | 主要控制 | 仍需承认的边界 |
|---|---|---|
| 修改宿主环境 | 隔离执行、无宿主敏感挂载、非 root、只读根、固定模板 | 内核/运行时漏洞仍可能突破普通容器 |
| 用户 A 读写用户 B | API/DB/对象存储/运行时四层 scope；只挂单工作副本 | 不用 UUID 难猜代替授权 |
| fork bomb/OOM/输出洪水 | cgroup/PID/输出/时长/磁盘限额、节点准入 | 限制必须真实测试，配置存在不代表生效 |
| 修改公共依赖/Skill | 不可变镜像、只读版本包、Run 内依赖目录 | 私有工作区仍可能残留恶意可执行文件 |
| 内网探测/元数据盗取 | 默认拒绝出网、受控 DNS/代理、阻断管理面和元数据 | 仅靠域名白名单不能阻止向合法目标泄露数据 |
| MCP 越权 | 每次工具/资源授权、用户/部门身份隔离 | 远端服务也必须校验权限，沙箱无法代替 |
| 提示注入 | 不可信内容标签、固定权限、工具网关、数据策略 | 不能仅靠 system prompt 彻底消除注入 |
| 审批后换代码/参数 | 不可变 ActionSpec/输入摘要、执行前复核 | 摘要覆盖不完整会留下 TOCTOU |
| Secret 出现在日志/模型 | SecretRef、最小凭据、注入代理、结构化脱敏 | 允许代码拿到的凭据，应视为该代码可读取 |
| 重启后重复写操作 | 持久意图、幂等键、结果核对、unknown 状态 | 非幂等远端无法通用 exactly-once |
| 预览 XSS/恶意文档 | 隔离域预览、无脚本渲染、解析沙箱、下载头 | 文件扫描不是“安全证明” |
| 共享缓存/记忆泄露 | scope+ACL revision 缓存键、来源与撤权传播 | 已经向外披露的内容无法靠删除缓存收回 |
| 运维绕过审计 | 职责分离、限时支持授权、独立审计存储 | root/DBA 权限仍需组织级控制 |

## 2. 信任分区

```text
A 浏览器/外部调用者
    ↓ 认证、CSRF、限流
B 控制服务：授权、调度、审批、业务状态
    ↓ 狭窄服务接口与 mTLS/短期身份
C 执行管理：节点代理、Sandbox Manager、固定镜像与挂载模板
    ↓ OS 隔离 + 配额 + 网络策略
D 不可信执行：Python/Node/Shell/浏览器/stdio MCP/文件解析器

E 外部业务服务/模型：经授权代理访问，不继承 B/C 的管理权限
F 持久数据：由服务身份按 scope 访问，不把通用数据凭据给 D
```

D 不可访问 Docker/Containerd Socket、Kubernetes API、控制 PostgreSQL/Redis、主机 SSH、云凭据端点、其他 D 实例。C 的运行时管理接口仅 B 的指定服务可调用；C 不提供任意主机命令执行。

## 3. 隔离运行时选择

| 方案 | 适用范围 | 代价/限制 | 本计划立场 |
|---|---|---|---|
| venv/workspace/cwd | 依赖组织与开发便利 | 没有 OS 级进程/网络/文件边界 | 不作为生产安全隔离 |
| 独立 OS 用户 + namespaces/cgroups | 特定内控环境 | 需要自行正确拼装大量安全与生命周期逻辑 | 不作为少人团队首选 |
| 加固 OCI 容器 | 已审核能力、受限内部试点 | 共享内核，需要完整挂载/网络/资源策略 | 可作为受限起点，完成全部 G2 测试 |
| gVisor 等增强隔离 | 较高不可信代码风险 | syscall/性能/浏览器/原生库兼容需验证 | 对开放代码优先评估 |
| Kata/微 VM | 更高隔离要求或敏感工作负载 | 虚拟化、镜像/启动/运维成本更高 | 视数据与风险要求选用 |
| 独立 VM/执行集群 | 强隔离部门、外部客户、高敏业务 | 成本最高，但权限边界更清楚 | 必要时按安全域分池，不追求一池承载所有风险 |

不先争论 Docker 是否“重”，先用代表性工作负载测量启动、RSS、CPU、浏览器与依赖兼容。普通容器与增强运行时暴露统一 SandboxBackend，避免业务代码绑定 Docker API。

Docker rootless/userns 可以减少权限，但须验证 cgroup v2、磁盘配额、网络限制在目标系统实际生效。不能为了某个包能运行而取消 cap_drop、开放 privileged 或挂载管理 Socket。

## 4. 固定 SandboxSpec

### 4.1 必填身份与模板

- org_id、run_id、generation、过期时间、节点、安全级别、profile_id、image_digest。
- workspace lease 和只读 Skill 包 digest。
- 网络 profile_id、允许的内部代理、DNS 规则。
- 每个执行单元独立 HOME、TMP、进程 namespace、依赖路径、浏览器 Profile、REPL session。
- 不能由普通用户提交 hostPath、capabilities、设备、namespace、sysctls、容器名或镜像 tag。

### 4.2 推荐默认安全参数

- `runAsNonRoot` 或等价的非 root UID/GID。
- `allowPrivilegeEscalation=false` / `no-new-privileges`。
- `cap_drop=ALL`，只在明确审查后增加极少能力；首版模板不允许增加。
- 不使用 `privileged`、host PID/network/IPC、宿主设备直通。
- 只读根文件系统；`/opt/runtime`、基础 Python/Node、Skill 包由镜像构建者拥有。
- `/workspace`、`/home/runner`、`/tmp` 等是独立、有配额的可写位置。
- 不挂宿主 `/`、`/etc`、`/proc`、`/sys`、用户 home、SSH agent、Docker socket。
- seccomp 与 AppArmor/SELinux 策略按运行时维护；不依赖“函数名黑名单”。
- 不把控制数据库/模型长期 Key/Secret 服务凭据放入容器环境变量。
- 不自动挂 Kubernetes service account token；管理 RBAC 与工作 Pod 分离。
- 执行 API 不发布到公网或员工可直连网段；默认用 manager 的受控通道访问。

浏览器可能需要特定 namespace/共享内存支持，必须单独测试。不能以“先用 --no-sandbox 跑起来”为通用生产修复；需要时改选兼容的隔离单元或独立浏览器服务，并重新评审。

### 4.3 目录建议

```text
/opt/runtime/              镜像内程序，只读
/opt/skills/<digest>/      本 Run 获权的版本包，只读
/workspace/               当前 Run 的项目工作副本，可写且有配额
/run-inputs/              固定输入对象，只读
/run-output/              候选产物，可写且有配额
/home/runner/             Run 私有 HOME，结束销毁
/tmp/                     Run 私有 tmpfs/临时卷，大小计入配额
```

不要把全部用户工作区挂进去再依靠 `/workspace/<user>` 命名区分。只挂当前获准访问的目录；需要多个项目输入时逐个只读授予。

## 5. 资源规格、容量与安装策略

### 5.1 起始 profile——必须压测调整

| profile | CPU 上限 | 内存上限 | PID 上限 | 临时写空间 | 单工具/Run 最长时间 | 首版范围 |
|---|---:|---:|---:|---:|---|---|
| parser | 1 vCPU | 1 GiB | 64 | 1 GiB | 180 s / 5 min | 隔离解析文档，无任意业务出网 |
| standard | 1 vCPU | 2 GiB | 128 | 2 GiB | 120 s / 10 min | 表格、脚本、轻量文档 |
| browser | 2 vCPU | 4 GiB | 256 | 4 GiB | 180 s / 15 min | 有浏览器需求且通过兼容测试 |
| heavy | 4 vCPU | 8 GiB | 256 | 10 GiB | 300 s / 30 min | 管理员批准，试点默认不开 |

- tmpfs 占用也计入内存，不把 tmpfs 当免费空间。
- 项目长期数据配额与 Run 临时空间分别计算；初始项目配额可为 5 GiB，需按业务确认。
- profile 上限不等于物理预留，准入必须控制可同时启动的总预算，防止过量超卖。
- 默认每用户 1 个本地执行 Run，组织最多 8 个本地执行 Run；RAG 等总活跃 Run 上限初始 10，解析池额外按全节点预算计入，不能绕过总量。
- 交互终端不继承“无限时间”；如后续开放，仍有活跃/空闲/总期限与输出限额。

### 5.2 限额必须对应真实实现

- CPU/内存/PID：通过实际运行时的 cgroup v2 controller 配置并读取验证结果；应用层 semaphore 只能做准入，不能代替内核限制。
- 磁盘字节/inode：Docker named volume 本身不提供通用硬配额。执行节点选择经验证的 XFS/project quota、固定容量文件系统/卷或具有等效硬配额的存储后端；卷的创建与 quota ID 由 manager 控制。
- 根文件系统只读，所有可写路径必须纳入受限卷/tmpfs。不能只限制 workspace 而留下无限可写 HOME、日志或 overlay 层。
- Kubernetes 的 ephemeral-storage request/limit 主要参与调度/驱逐治理，不能不测试就当成逐字节即时硬隔离；必要时叠加卷配额和节点水位保护。
- I/O 带宽/IOPS 视后端用 io controller 或存储 QoS，至少通过准入和隔离执行节点避免拖垮控制数据库。
- backend 不支持所需硬限制时，不声称通过 G2；降低开放能力或切换后端，而不是用“定期清理”替代资源安全。

### 5.3 参考容量算式

例：16 vCPU / 64 GiB 执行节点，至少预留 4 vCPU / 16 GiB 给系统、manager、镜像与故障余量，准入预算不超过 12 vCPU / 48 GiB。6 个 standard + 2 个 browser 的声明上限合计 10 vCPU / 20 GiB；另有 parser 时同样计入 CPU/内存预算。

这只说明声明额度可放下，不保证响应时间或最大吞吐。还需测磁盘 IOPS、内网/外网、浏览器峰值、镜像拉取和外部模型限流。初期可不内存超卖；超过配额排队，不无限并发。

磁盘还需计算 `镜像层 + 活跃临时卷 + 日志上限 + 下载缓存 + 保留失败副本 + 余量`。对象存储容量不等于执行节点本地磁盘容量。调度器监控字节和 inode；达到安全水位停止分配新任务，不能等根盘写满。

### 5.4 依赖安装

1. 系统包、浏览器、字体、Office 转换器通过可信 CI 构建镜像，不在任务里 `sudo apt install`。
2. Python 用 Run 私有 `.venv`，Node 用 Run 私有项目目录；不写公共 site-packages 或全局 npm。
3. 优先使用审核依赖与内部镜像仓库；锁文件、哈希和版本进入 SkillVersion/镜像元数据。
4. 安装脚本、wheel/native addon 构建本身也是不可信执行，受同样沙箱和网络约束。
5. 跨用户共享包缓存只读且来源可信；用户可写缓存不回灌公共仓库，避免供应链污染。
6. `.venv`、`node_modules`、浏览器 Cookie、临时启动脚本不默认作为项目正式产物发布。
7. 缺依赖先报业务可理解错误或申请新镜像；不得为了完成任务提升宿主权限。

## 6. 执行协议与有界输出

执行器必须支持：

- run_id/generation、logical_execution_id、language/entrypoint、代码或文件引用、固定 cwd。
- 工具级超时、Run 总 deadline、stdout/stderr 分开流式输出、退出码、OOM/超时/取消原因。
- 有界读取，避免 `capture_output=True` 将无限输出先存内存再截断。
- 建议起始：每 chunk <= 64 KiB、内存缓冲 <= 256 KiB、工具原始返回 <= 1 MiB，实际入模摘要另受 token 预算限制、每次执行累计日志 <= 10 MiB。超限截断并终止持续洪水，返回 `OUTPUT_LIMIT_EXCEEDED`。
- 不只 kill 外层 Shell：使用进程组/cgroup/容器级停止，处理子孙进程、后台服务器、Node timers、浏览器进程树。
- stdin、代码、文件路径、输出文件数量/总大小均有限制；拒绝无界交互输入。
- runner 失联后 manager 的硬 deadline 独立生效，不能只靠应用 asyncio timeout。
- CancelledError/网络断开不自动当成执行完成；由 manager 查询/停止并确认状态。

沙箱内部 API 被恶意代码杀掉是允许发生的局部故障；manager 在外部收回容器。不能把沙箱内部服务报告的“我已经清理”当成唯一可信证据。

## 7. 沙箱生命周期与重建

### 7.1 正常流程

`预算与授权 → 工作区租约 → 幂等创建 → 健康检查 → 执行 → 保存候选输出 → 发布 → 撤销执行能力 → 销毁 → 对账`

- 健康检查只说明运行时 ready，不代表安全测试通过。
- 同一 Run 的同权限计算工具复用 compute cell；不会每一步都重建。持有业务凭据的 connector、解析器等按权限域使用独立 target cell；同 Run 不等于所有进程共享 Secret。
- 审批等待期间可以保留沙箱但继续计入配额，初始审批期限 5 min，不无限延长任务。
- 审批期间若容器被回收，不能假设内存/文件状态不变；失效审批并结束或进入明确恢复流程。
- 普通任务结果持久化后销毁；排障保留是例外，必须限时、隔离、撤销出网和凭据。

### 7.2 Reaper 与孤儿检测

后台按 run_id/generation 标签对账 PG 与运行时：

- PG 有 lease、节点无实例：标记丢失，关闭执行资格，按任务可恢复性处理。
- 节点有实例、PG 无有效 lease：隔离并销毁孤儿实例，记录原因。
- Run 已结束、沙箱仍存在：重试清理；超过阈值隔离节点，暂停新调度。
- Worker 过期：撤销 generation，终止旧沙箱，不让旧代码和新 Run 同时写同一工作区。
- 到期卷/浏览器 Profile/临时目录与容器独立清理，按精确资源 ID，而不是广泛路径删除。

跨用户复用只允许**从干净镜像新建实例**。预热池保存未执行用户代码、无用户凭据和文件的实例；一旦租给用户，回收后销毁，不清空目录后回池。

## 8. 网络访问矩阵

| 来源 → 目标 | 默认策略 | 允许条件 |
|---|---|---|
| 浏览器 → API | 允许 HTTPS | 有效登录、CSRF/Origin/限流 |
| 浏览器 → sandbox/manager/DB/Redis | 拒绝 | 不开放直接访问 |
| API/Worker → manager | 受限允许 | 服务身份、固定请求 schema、org/run/generation |
| sandbox → 控制 API/DB/Redis/容器引擎/K8s API | 拒绝 | 无通用例外 |
| sandbox → 其他 sandbox | 拒绝 | 不因同用户而默认互通 |
| sandbox → 公网 | 拒绝 | 对应 profile 经 egress proxy 放行最小目标 |
| sandbox → 包仓库 | 拒绝 | 仅批准的镜像/仓库，限制方法/目标并记录 |
| sandbox/stdio MCP → 业务端点 | 拒绝 | 连接器明确登记、身份和资源最小化 |
| Worker → 模型端点 | 受控允许 | 已批准 endpoint 与数据策略、预算、对应凭据 |
| ToolGateway → 远端 MCP | 受控允许 | 连接获授权，目标校验，逐次业务授权 |
| 知识解析器 → 任意 URL | 拒绝 | 默认不跟随文档内远程内容 |

防 SSRF 细节：

- URL scheme、端口、域名和解析 IP 都校验，防 DNS rebinding、重定向到内网、IPv6/IPv4-mapped/非标准表示绕过。
- 默认阻断 loopback、link-local、元数据端点和内网管理网段；确需业务内网访问，只允许显式业务代理或审批连接器地址。
- 连接后的真实目标必须符合策略，不能只在保存 URL 时检查一次。
- 代理环境变量可被脚本绕过，因此需要主机/运行时层网络控制；DNS 也经受控解析器。
- MCP 返回的 resource link、浏览器重定向、网页子资源和“测试连接”也遵守同样策略。
- 不能把默认 `internal: true` 网络解释为“无法访问同网络里的 Harness”。

允许访问某域名仍可能向该域名发送数据。因此外发还需要数据分级、连接器动作约束和必要的 DLP；不能仅凭 allowlist 宣称防泄露完成。

## 9. 凭据与身份

### 9.1 推荐路径

- 模型和远程业务长期凭据保留在 Secret 服务/受控代理，不注入通用沙箱。
- 远程 MCP 由可信 Gateway 代调用，连接池按 org+owner/scope+connection+credential revision 隔离。
- 必须在 stdio MCP 内使用的 Secret，按连接器拆分、短期、最小 scope，并默认放在独立 connector cell。任意 compute 代码不能共用其文件/进程权限或直接业务出口；若实际同域，须承认同域代码可读取凭据且工具审批可能被绕过，不能按强隔离方案放行。
- 沙箱确需调用平台工具时，只拿绑定该 Run/generation/允许工具/截止时间的受限 capability，不能获得全局 Bearer。
- capability 校验包含 issuer、audience、expiry、nonce/jti、run 状态、generation 和当前撤权状态；有效签名不代表当前仍获权。

### 9.2 不能采取的方式

- 共享管理员 MCP Token 给全公司。
- Secret 存在 Skill 文本、用户可读模型配置或工作区 `.env`。
- 把任意用户 `apiKey: !command` 当作生产配置执行。
- 默认用一个 provider 的 Key 回落给另一个 endpoint。
- 在 URL query 放长期 Token；日志/Referrer/截图可能泄漏。
- 为诊断方便把容器完整 env、命令行、HTTP Authorization 原样导出。

### 9.3 撤销与轮换

- Secret 轮换增加 binding revision，关闭旧连接池；排队任务使用当前有效绑定或明确失败。
- 用户离职/连接撤销后阻止下一次模型/工具动作，并终止关联受限运行时。
- 不能保证撤销已被外部服务接受的请求；需审计已有影响。
- 所有 Token 和 Secret 出现事故时有定位受影响 Run/连接/资源的索引，支持批量禁用与轮换。

## 10. 文件、上传、解压与产物安全

### 10.1 上传与解压

- 初始单文件上限建议 50 MiB，可按业务放大；流式累计真实字节，不信任 Content-Length。
- 验证用途、扩展名和实际类型，存储使用服务端生成 ID；原始文件名只用于显示。
- ZIP/TAR 处理设置解压总大小、文件数、层级、压缩比、时间限制；拒绝绝对路径、`..`、硬链接/符号链接/设备节点等非预期条目。
- 对路径实施实际边界检查，并防检查后替换链接的 TOCTOU；Linux 可用 dirfd/no-follow 或等价安全文件 API。
- 上传区与发布区分开；扫描未完成的对象不能从正常下载 API 访问。

### 10.2 文档与预览

- PDF/Office/OCR/图片解码器放入 parser 沙箱；禁宏、禁外链加载、禁任意出网。
- HTML/SVG/可执行文件默认下载或无脚本隔离预览；不用控制台同域 iframe 执行用户页面。
- 预览域无平台 Cookie；CSP、Content-Disposition、X-Content-Type-Options、链接 rel 属性等进入前端安全测试。
- Markdown 结果继续使用经过维护的 sanitizer，工具/文档输出不得绕过清洗直接 innerHTML。

### 10.3 产物收集与发布

- 执行进程停止/冻结后才收集候选文件，防读取时被并发替换。
- 收集器使用已绑定卷和安全文件遍历；不直接执行候选文件，不相信沙箱自报的路径/大小/hash。
- 限制单 Run 产物数量、单文件与总大小；默认排除 `.venv`、node_modules、Cookie、凭据文件和系统临时内容。
- 上传对象使用不可变键；扫描通过并写入 Artifact ACL 后才发布。
- 签名 URL 相当于短期 bearer：建议几分钟内失效。需要即时撤回的敏感下载走授权代理，不能声称已发出的签名 URL 会自动失效。

## 11. 权限与审批实施细则

### 11.1 策略层级

`组织硬约束 ∩ 部门/项目授权 ∩ Agent 版本能力上限 ∩ 用户连接权限 ∩ Run 当前状态 ∩ 工具参数资源范围`

没有一层可以扩大上层权限。Skill 提示、模型建议、“管理员模式”等文本不参与信任判断。

### 11.2 风险等级

| 风险 | 示例 | 默认动作 |
|---|---|---|
| R0 受限只读 | 已授权 KB 检索、读取明确业务记录 | 自动允许，仍校验身份和记录审计 |
| R1 沙箱内局部写 | 私有文件生成、受限代码计算 | 在安全 profile 内预授权，不逐条让业务用户猜命令 |
| R2 外部业务写 | 创建工单、发消息、更新少量记录 | 明确业务影响、最小凭据、审批、幂等与结果查询 |
| R3 高危/广域写 | 批量删除、权限授予、支付、系统管理 | 试点禁止；专门评审、双人审批或仍保持禁止 |

MCP 自报的 readOnly/destructive 注解只作提示，风险由管理员和策略确定；不能信任第三方把写工具标为只读。

审批的对象是具体动作，不是“允许这个 Agent 以后随便操作”。审批超时默认拒绝，连接断开不能变成默认允许。

### 11.3 派生数据与分享的权限传播

只保护原文检索还不够：员工可以让 Agent 把受限文档整理成新报告，再尝试分享给全公司。V1 对一个 Run 接触的来源做保守追踪：

- 输入文件、知识片段、MCP 结果的来源、数据级别与分享限制进入 provenance。
- 回答、摘要、工作区发布版本和 Artifact 至少继承最严格的数据级别与适用来源限制；新文件不是“无来源的普通文件”。
- 分享/外发时，除 Artifact 自身 Grant，还检查收件人是否满足来源策略；不能只因为用户是产物 owner 就允许降级公开。
- 多来源权限无法可靠合并时保持私有/禁止扩大分享，或走明确的脱敏与解除限制审批；不是让模型自报“已脱敏”就放行。
- 若工具返回数据级别高于当前已批准模型/profile，先拒绝外发并引导新建合规任务；不得临时偷偷换 Provider 或降低标签。
- 提示词中的“这是公开资料”不能修改服务端来源标记。人工新输入的标签仍需要组织的数据治理，系统不能保证识别所有语义泄露。

## 12. 日志、审计与运维访问

- 普通日志：错误码、耗时、资源、关联 ID；不默认记录完整 prompt/文件/工具结果。
- 安全审计：身份、动作、资源、策略、审批、目标连接、结果和摘要，追加写。
- 高风险动作在可靠写入意图/审批/审计前不得执行；审计不可用时 fail closed。遥测系统故障不必阻断所有低风险业务，但必须告警并有安全事实存储。
- Secret 字段按 schema 分类脱敏，不能只靠正则识别 `sk-`；URL/header/body/env/异常链都要处理。
- 截图和文档可能包含 PII，不能由简单字符串脱敏代替内容授权。
- 生产调试必须申请 support grant；记录谁在何时查看了什么字段；到期自动收回。
- 审计归档可使用独立权限的不可变/保留锁存储，但要承认存储管理员和密钥管理的组织控制边界。

## 13. 安全故障默认行为

| 故障 | 应采取的行为 |
|---|---|
| SSO/权限服务无法确定身份 | 拒绝新业务动作，不用缓存的宽松角色兜底 |
| manager/沙箱不可用 | 排队/失败，不在 Harness 宿主执行 |
| Secret 读取失败 | 明确凭据故障，不换用公共管理员 Token |
| 预算无法校验 | 暂停新计费调用，高风险请求不继续 |
| DB/持久审计不可写 | 停止新增副作用；保存可保存的信息，恢复后核对；不盲目重新执行 |
| Redis 不可用 | 降级为受限 DB 扫描/事件轮询；权限和计费事实仍在 PG |
| 节点磁盘达到水位 | 停止调度、清理已到期资源，不删除活跃用户数据 |
| 无法确认进程树已停止 | 沙箱隔离/节点标记异常，禁止复用，告警 |
| 外部写请求结果不明 | 标记 recovery_required，人工或查询核对 |
| 恢复备份 | 先重放删除/撤权/禁用记录，再恢复业务访问 |

## 14. 上线前必须给出的安全证据

1. 两个并发沙箱不能互读、互改、互连；同名文件仍隔离。
2. 所有执行器包括 browser、Node、stdio MCP、parser、管理员测试入口没有宿主执行旁路。
3. 验证非 root、挂载、只读根、capabilities、seccomp、网络、CPU/内存/PID/磁盘限制实际生效。
4. 代码不能读取控制服务的长期 Secret；过滤 env 的单元测试不足以证明这一点。
5. 大输出、无限循环、子进程、磁盘/inode 耗尽只影响当前隔离单元；控制面保持服务。
6. Worker/manager 崩溃和 API 回复丢失不会产生无法追踪的沙箱或重复外部写入。
7. 资源授权覆盖 HTTP、SSE、WS、下载、审批、缓存、RAG 和运维支持。
8. 第三方 Skill/MCP/文档的恶意指令不能更改服务端身份、权限与网络策略。
9. 版本禁用、用户离职、凭据轮换、应急停止能够阻止下一次调用。
10. 记录未解决风险、运行时限制和已接受的试点范围；不能将“内网部署”当作安全结论。
